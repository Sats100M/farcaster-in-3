Quickstart

Up and running

About ten minutes of your time, plus a few hours of the node syncing on its own.

Node.js 20+on your own computer
A cloud accountAzure, AWS or Hetzner (which?)
A Farcaster accountwith storage, and its recovery phrase
0

Rent a server

git clone https://github.com/Sats100M/farcaster-in-3 && cd farcaster-in-3
az login       # or: aws login, or HCLOUD_TOKEN=... in .env for Hetzner
node scripts/provision.mjs --provider azure

Shows the price and asks before creating anything. You get a 4 vCPU / 16 GB server with a 2 TB disk and the Snapchain ports open, and it prints command 1 for you.

1

Start a Snapchain read node

ssh -i ~/.ssh/farcaster_node azureuser@<server-ip> \
  "curl -fsSL https://raw.githubusercontent.com/Sats100M/farcaster-in-3/main/scripts/node.sh | sudo bash -s -- --fid <your-fid>"

Installs Docker and the official Snapchain node, then starts syncing. The first sync pulls a ~470 GB snapshot and takes several hours. Run fc-node-status on the server to watch it.

2

Run the client

cd client && npm install
node fc.mjs init --node <server-ip>

Asks for your recovery phrase once, uses it to give this client its own app key, and forgets it. Then:

node fc.mjs feed                         # people you follow
node fc.mjs cast "posting from my own node"
node fc.mjs follow dwr
node fc.mjs like 3/0x…                   # ids are shown in the feed
node fc.mjs feed --hide-app <app>        # filter by client
⚠

Treat your recovery phrase like rm -rf. It controls your account. Only paste it into software you have read or trust. This client uses it in memory to sign one message and never stores or sends it, but check that yourself: it's one file.

Trying this for the first time? Use a test account, not your main one.

Done for now? node scripts/destroy.mjs --provider azure deletes everything so billing stops.

Concepts

How Farcaster fits together

A social network split into layers that different people run. No single app owns your account.

Optimism

Identity

Your account number (FID), the wallet that owns it, and the storage you've paid for live in smart contracts on Optimism.

Snapchain

Data

Casts, likes, follows and profile info. Each one is a small signed message, stored by every node on Farcaster's own network.

Anyone's code

Apps

The feed you scroll and the post button. Any software can be a client, including the one in this repo.

If one app bans you or shuts down, your FID, followers and casts are still on the network, and any other client can show them. Running your own node and client is the most direct way to see that for yourself.

FIDs and custody addresses

An FID is your account number, issued by the ID Registry contract on Optimism. Usernames like @dwr are a separate label that points to an FID.

The custody address is the Ethereum wallet that owns the FID, derived from your recovery phrase (m/44'/60'/0'/0/0). It can transfer the account and add or remove app keys, so you use it to authorize things, never to post.

Storage rent

Every message takes space on every node, so accounts pay rent. Storage is bought in yearly units on Optimism; one unit holds roughly 5,000 casts, 2,500 reactions and 2,500 follows. Go over, and the oldest messages of that type are pruned.

Accounts made in the Farcaster app usually come with storage. This client can't post for an account that has none.

Snapchain, validators and read nodes

Snapchain orders and stores every Farcaster message. It's split into shards, and your FID decides which shard your messages go to.

Validators are a small, known set of nodes that propose and vote on blocks, chosen through an onchain config. Read nodes run the same software with read_node = true: they follow the chain, keep the full state, and serve the same HTTP (3381) and gRPC (3383) APIs. Anyone can run one, and that's what step 1 sets up.

Can you post through a read node? Yes. A read node has no mempool of its own. When you submit a message it checks that it's valid and new, gossips it to the network, and keeps nothing. A validator picks it up and puts it in a block, which then syncs back to your node. So "success" from your node means accepted and relayed, not included. Under heavy load a relayed message can get lost; the client shows the cast's ID so you can check it landed.

App keys

Apps don't post with your custody key. Each app gets its own app key (a signer): an Ed25519 key pair that can sign messages for your FID and nothing else.

Since mid-2026, adding one doesn't need an Optimism transaction. The client sends a KEY_ADD message straight to Snapchain, carrying three signatures:

  1. Your custody address signs an EIP-712 KeyAdd: which key, which message types it may sign, how long it lives, and a nonce.
  2. The requesting app's custody address signs a SignedKeyRequest naming the app's FID. This client acts as its own app, so that's your custody address again.
  3. The new key itself signs the message envelope, proving whoever added it actually holds it.

The key in this client may only post, delete casts, react and follow. It can't add other keys or touch the account. It expires after 30 days without use, and every use pushes that back. The older onchain route (the KeyGateway contract) still works and never expires, but costs gas.

Steps 0 and 1 in detail

The server and the node

Snapchain asks for 4 cores, 16 GB RAM, a public IP, ports 3381–3383 open (3382 is UDP), and a lot of disk.

The docs say 1.5–2 TB. We measured the first sync: the snapshot is about 5,700 chunks of ~82 MB, so ~470 GB compressed, and the chunks stay on disk while it unpacks. Use 2 TB. provision.mjs creates exactly that, tags everything, and destroy.mjs removes it all.

Provider notes, from actually doing it

ProviderWhat to know
AzureNew subscriptions have Compute switched off until it's registered; the script does it. Free trials get 4 vCPUs per region, exactly enough. Popular sizes sell out per region; the script falls back to other sizes and regions. Trial credit expires after 30 days.
AWSFree-plan accounts can't launch anything this big. Upgrading keeps your credits, but accounts made with the new "Projects" experience still block EC2 and Lightsail until advanced features are activated. Lightsail (--provider lightsail) includes 6 TB of transfer.
HetznerCheapest once your account is established. Brand-new accounts can't create a volume this big and can't ask for a higher limit yet.

What node.sh does

It wraps the official installer from farcasterxyz/snapchain and adds three things: it formats and mounts the data disk and keeps the database there; it pre-answers the installer's prompts, which otherwise read from the keyboard and break over SSH; and it installs fc-node-status, which shows snapshot progress and then how far behind each shard is.

A new node downloads the snapshot (several hours), restores it, then catches up block by block. It's synced when every shard is a few seconds behind. A weekly cron job keeps it upgraded.

fc-node-status                                  # on the server
curl http://<ip>:3381/v1/info                    # from anywhere
curl "http://<ip>:3381/v1/castsByFid?fid=3&pageSize=3&reverse=1"
Step 2 in detail

The client

One file, client/fc.mjs, on the official @farcaster/hub-nodejs library. It only ever talks to the node you give it.

init

Derives your custody address from the phrase, finds your FID on your node, creates an app key, submits the KEY_ADD, and waits until the key appears in a block. Only the app key is saved, in ~/.farcaster-in-3.json.

feed

Reads who you follow, pulls their latest casts from your node, and merges them by time. Nothing ranked, nothing hidden, except what you choose to filter.

cast · follow · like · recast

Builds the message, signs it with the app key, and submits it to your node, which relays it to the validators.

Filter by client

Every message is signed by an app key, and every app key records the FID of the app that requested it (requestFid). Your node knows which app each cast came from, without trusting the app.

node fc.mjs apps dwr                  # which apps a user posts from
node fc.mjs feed --only-app <app>     # only casts made in that app
node fc.mjs feed --hide-app <app>     # everything except that app

<app> is the app's username or FID, as listed by fc apps.

Troubleshooting

fc init can't reach the node

The API only comes up after the snapshot is restored. Run fc-node-status on the server, and check port 3383 is open (the provision script opens it).

"nonce is not greater than stored nonce"

Another key was added for your FID at the same moment. Run init again.

My cast doesn't show up in other apps

Give it a few seconds. If it never appears, the relay was dropped under load: post it again.
