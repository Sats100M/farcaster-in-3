Your own Farcaster, in three commands

A Snapchain read node on a server you rent, and a client on your laptop that reads from it and posts through it. No API keys, nobody's permission.

Source on GitHub (MIT)

Quickstart

You need: Node.js 20+, an account with a cloud provider (Azure, AWS or Hetzner, see which one), and a Farcaster account that has storage, with its recovery phrase.

0

Rent a server

git clone https://github.com/Sats100M/farcaster-in-3 && cd farcaster-in-3
az login     # or: aws login, or put HCLOUD_TOKEN in .env for Hetzner
node scripts/provision.mjs --provider azure

Shows the price, asks, then creates a 4 vCPU / 16 GB server with a 2 TB disk and the right ports open. It prints command 1 for you.

1

Start a Snapchain read node

ssh -i ~/.ssh/farcaster_node azureuser@<server ip> \
  "curl -fsSL https://raw.githubusercontent.com/Sats100M/farcaster-in-3/main/scripts/node.sh | sudo bash -s -- --fid <your fid>"

Installs Docker and the official Snapchain node, then starts syncing. The first sync downloads a ~470 GB snapshot and takes several hours. Check with fc-node-status on the server.

2

Run the client

cd client && npm install
node fc.mjs init --node <server ip>

Asks for your recovery phrase once, uses it to give this client its own app key, and forgets it. Then:

node fc.mjs feed
node fc.mjs cast "posting from my own node"
node fc.mjs follow dwr
node fc.mjs like 3/0x…
node fc.mjs feed --hide-app <app>

About the seed phrase. Your recovery phrase controls your account. Treat pasting it like running rm -rf: only do it in software you have read or trust. The client uses it in memory to sign one message and never stores or sends it, but you should check that yourself (it's one file).

If you're trying this for the first time, use a test account, not your main one.

When you're done: node scripts/destroy.mjs --provider azure deletes everything so billing stops.

How Farcaster fits together

Farcaster splits a social network into three layers, run by different people:

LayerWhat lives thereWhere
IdentityYour account number (FID), which wallet owns it, your app keys if added onchain, storage you've paid forSmart contracts on Optimism (an Ethereum L2)
DataCasts, likes, follows, profile info, each one a small signed messageSnapchain, Farcaster's own network of nodes
AppsThe feed you scroll, the post buttonAnyone's software, including the client in this repo

No single app owns your account. If one app bans you or shuts down, your FID, followers and casts are still on the network, and any other client can show them. Running your own node and client is the most direct way to see that for yourself.

FIDs and custody addresses

An FID (Farcaster ID) is your account number, an integer issued by the ID Registry contract on Optimism. Usernames like @dwr are a separate, changeable label that points to an FID.

The custody address is the Ethereum wallet that owns the FID. Its private key comes from your recovery phrase (the standard Ethereum path, m/44'/60'/0'/0/0). Whoever holds it can transfer the account, add or remove app keys, and change the recovery address. That's why you only use it to authorize things, never for day-to-day posting.

The client looks up which FID your custody address owns by asking your own node (getIdRegistryOnChainEventByAddress). Nodes follow the Optimism contracts, so no Ethereum RPC or API key is needed.

Storage rent

Every message takes up space on every node, so accounts pay rent for it. Storage is bought in units on Optimism, and each unit lasts a year. One unit holds roughly 5,000 casts, 2,500 reactions and 2,500 follows. When you go over, the oldest messages of that type are pruned to make room.

Most accounts made through the Farcaster app come with storage already. The client in this repo needs an account that has some: it can't post for an account with none.

Snapchain, validators and read nodes

Snapchain is the network that orders and stores Farcaster messages. It's split into shards; your FID decides which shard your messages go to.

Validators are a small, known set of nodes that propose and vote on blocks. You can't become one by running software; they're chosen through an onchain config.

Read nodes run the same software with read_node = true. They follow the chain, keep the full state, and serve the same HTTP (port 3381) and gRPC (port 3383) APIs. Anyone can run one. That's what step 1 sets up.

Can you post through a read node? Yes. A read node has no mempool of its own: when you submit a message it checks that it's valid and new, gossips it to the network, and keeps nothing. A validator picks it up from gossip and puts it in a block. So "success" from your node means accepted and relayed, not included. Under heavy load a relayed message can get lost and need resending; the client shows the cast's ID so you can check it landed.

App keys

Apps don't post with your custody key. Each app gets its own app key (also called a signer): an Ed25519 key pair that can sign messages for your FID and nothing else.

Since mid-2026, adding an app key doesn't need an Optimism transaction. The client sends a KEY_ADD message straight to Snapchain, carrying three signatures:

  1. Your custody address signs an EIP-712 KeyAdd: which key, which message types it may sign, how long it lives, and a nonce.
  2. The requesting app's custody address signs a SignedKeyRequest naming the app's FID. Here the client acts as its own app, so it's your custody address again.
  3. The new key signs the message envelope, proving whoever added it actually holds it.

The key in this client may only post, delete casts, react and follow. It can't add other keys or touch the account. It expires after 30 days without use, and every use pushes that back. The older onchain way (the KeyGateway contract) still works and those keys never expire, but it costs gas.

Step 0 in detail: the server

Snapchain's stated requirements: 4 CPU cores, 16 GB RAM, a public IP, ports 3381–3383 open (3382 is UDP), and a lot of disk. The docs say 1.5–2 TB. We measured the first sync: the snapshot alone is about 5,700 chunks of ~82 MB, so ~470 GB compressed, and it stays on disk while it unpacks. Use 2 TB.

provision.mjs creates exactly that, tags everything, and destroy.mjs removes it all. Things we hit on each provider:

ProviderWhat to know
AzureNew subscriptions have Compute switched off until it's registered; the script does it. Free trials get 4 vCPUs per region, exactly enough. Popular sizes are often sold out in a region; the script tries other sizes and regions. Free-trial credit expires after 30 days.
AWSFree-plan accounts can't launch anything this big. Upgrading keeps your credits, but accounts created with the new "Projects" experience still block EC2 and Lightsail until you activate advanced features. Lightsail (--provider lightsail) includes 6 TB of transfer.
HetznerCheapest for an established account. Brand-new accounts can't create a 1 TB+ volume and can't request a higher limit yet.

Step 1 in detail: the node

node.sh wraps the official installer, farcasterxyz/snapchain's snapchain.sh. It adds three things:

  • It formats and mounts the big data disk and keeps the node's database there.
  • It pre-answers the installer's prompts (it asks you to agree there are no rewards for running a node, and for an FID to pick an auto-upgrade day). The official bootstrap reads those from the keyboard, which breaks when piped over SSH.
  • It installs fc-node-status, which shows snapshot progress and then how far behind each shard is.

A new node downloads a snapshot first (several hours), restores it, then catches up block by block. It's synced when every shard is a few seconds behind. A weekly cron job upgrades the node automatically.

fc-node-status                       # on the server
curl http://<ip>:3381/v1/info         # from anywhere
curl "http://<ip>:3381/v1/castsByFid?fid=3&pageSize=3&reverse=1"

Step 2 in detail: the client

The client is one file, client/fc.mjs, built on the official @farcaster/hub-nodejs library. It only ever talks to the node you give it.

  • init derives your custody address from the phrase, finds your FID on your node, creates an app key, submits the KEY_ADD, and waits until the key shows up in a block. Only the app key is saved, in ~/.farcaster-in-3.json.
  • feed reads who you follow, fetches their latest casts from your node, and merges them by time. Nothing is ranked or hidden by anyone but you.
  • cast, follow, like, recast build a message, sign it with the app key and submit it to your node, which relays it to the validators.

Filtering by client

Every message is signed by an app key, and every app key records the FID of the app that requested it (requestFid). So your node knows which app each cast came from, without trusting the app.

<app> is the app's username or FID, as listed by fc apps.

node fc.mjs apps dwr                 # which apps a user posts from
node fc.mjs feed --only-app <app>    # only casts made in that app
node fc.mjs feed --hide-app <app>    # everything except that app

Troubleshooting

fc init says it can't reach the node

The API only comes up after the snapshot is restored. Run fc-node-status on the server. Also check port 3383 is open (the provision script opens it).

"nonce is not greater than stored nonce"

Another key was added for your FID at the same moment. Run init again.

My cast doesn't show up in other apps

Give it a few seconds. If it never appears, the relay was dropped under load: post it again.
